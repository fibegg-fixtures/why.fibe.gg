# Запусти спочатку локально

Fibe — це тонкий, з характером, врапер навколо найрозгорнутішого у світі інструменту оркестрації: **Docker Compose**. Твоє джерело правди — звичайний `docker-compose.yml`. Нічого зверху, нічого кастомного, нічого пропрієтарного.

Один цей факт відкриває спосіб роботи, який інші платформи не можуть до кінця скопіювати.

## Що насправді означає "тонкий врапер"

- **Жодного platform-specific YAML.** Ні `fibe.yml`, ні особливого build-маніфесту, ні DSL для вивчення. Файл, який ти написав би, щоб запустити сервіс на ноуті — це той самий файл, який читає Fibe.
- **Жодного шару трансляції.** Fibe не компілює твій compose-файл у щось інше. Він його запускає. Той самий `docker compose up`, який ти набрав би в терміналі — це те, що відбувається всередині.
- **Без vendor lock-in.** Якщо Fibe завтра зникне, твоє репо все одно працює. Будь-хто з ноутом і Docker підніме той самий стек.

## Локально → CI → продакшен

Killer use case — це **верифікація CI/CD до деплою**. Більшість платформ "задеплой свій стек" змушує тебе пушнути зміну, подивитись, як вона ламається в їхньому пайплайні, пушнути ще одну, подивитись, як ламається *вона*, повторювати годину.

З Fibe:

1. **Редагуєш `docker-compose.yml` на ноуті.**
2. **Запускаєш локально.** `docker compose up` — рівно те, що зробив би Fibe.
3. **Ітеруєш, поки сервіси не піднімаються, health-чеки не проходять, тести не зеленіють.** Усе на твоїй машині. Нуль раундтріпів до віддаленої системи.
4. **Тільки потім пушиш у Fibe.** Що працювало локально — працює там. Той самий compose, ті самі образи, та сама форма мережі.

Цикл, який раніше займав 30 хвилин (push → чекай → впав → фікс → push → чекай…), займає секунд 30 (`docker compose up` → фікс → `docker compose up`).

## Що тобі дає "детермінізм"

- **Відтворювані баг-репорти** — "у мене на машині працює" перестає бути мемом. Твоя машина і Fibe ганяють той самий compose-граф на тих самих образах.
- **Реальна офлайн-розробка** — сів у літак, працюєш по повному стеку без мережі, пушиш коли приземлився. Ніщо в платформі не потребує конективіті для роботи.
- **Air-gapped деплої** — клієнт без інтернету може запустити твій продукт. Передаєш йому compose-файл, образи і платформу — він запускає на своєму залізі так само, як ти.
- **Безпечні міграції** — переїзд між серверами Fibe, між регіонами, між Fibe і self-hosted: той самий compose-файл. Жодного "migration script" писати не треба.

## Що ми додаємо зверху

Врапер-частина — це і є value-add:

- **Публічні URL для кожного сервісу** — Fibe бере на себе роутинг, сертифікати, DNS, щоб ти не сипав ngrok по compose-файлу.
- **Клонування середовища в один клік** — зроби копію живого стеку для тіммейта, експерименту, демо клієнту.
- **Точки інтеграції з AI** — агенти можуть читати/писати compose-файл, виконувати команди всередині живого стеку, забирати артефакти. (Опційно, дефолтом вимкнено.)
- **Веб-UI для живого стеку** — логи, термінал, файловий браузер, редактор env-змінних. Те саме, що хочеш мати на проді, доступно з браузера.

Ніщо з цього не міняє, як працює базовий compose. Воно сидить *навколо* нього.

## Одним реченням

> **Що працює локально через `docker compose up`, працює на Fibe. Що працює на Fibe, працює локально через `docker compose up`. Іншого контракту немає.**

Це нудна обіцянка. Саме та, яка робить систему достатньо стабільною, щоб поставити на неї компанію.
